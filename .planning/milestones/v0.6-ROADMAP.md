# Milestone v0.6: Engine Architecture

**Status:** ✅ SHIPPED 2026-06-25
**Phases:** 44-45
**Total Plans:** 9 (Phase 44: 6, Phase 45: 3)

## Overview

Made `Engine` own its ADBC connection pool and dialect (SQLAlchemy-style), serving
both introspection and execution from one object. `create_engine(config | name)` +
`register("name", engine)` replaced the bare `(pool, dialect)` tuple registry. Native
backend connectors were removed — the stack is ADBC-only. This was a clean break of
the v0.5 connection API (pre-1.0, no deprecation path). On top of the new architecture,
Databricks query execution was brought fully online over real ADBC: literal-inlined
WHERE values (the arrow-adbc Databricks driver has no bind parameters), an
adbc-poolhouse DSN fix carrying `catalog`/`schema`, and the first recorded Databricks
integration cassettes. A follow-up after Phase 45 also implemented Databricks ADBC
introspection (retiring the Phase 44-04 `NotImplementedError` fallback) once the ADBC
Databricks driver proved present on the dev machine.

## Phases

### Phase 44: Engine Owns the Pool

**Goal**: Make `Engine` own its ADBC pool + dialect and serve both introspection and
execution from it; `create_engine(config | name)` + `register("name", engine)` replace
the `(pool, dialect)` tuple. ADBC-only — native connectors removed. Clean break of the
v0.5 connection API (pre-1.0).
**Depends on**: Phase 43 (and the `gsd/pytest-adbc-replay-migration` branch — qmark
placeholder + view-name folding)
**Plans**: 6 plans in 4 waves

Plans:

- [x] 44-01: Wave 0 test bedrock — rewrite unit tests + shared fixtures to the
  `create_engine` / `register(engine)` / `get_engine` / ADBC-cursor contract (RED)
- [x] 44-02: Core — `Engine` owns pool+dialect (`connect()` + concrete ADBC
  `execute()`); `create_engine()` factory; registry collapsed to name→Engine
- [x] 44-03: Snowflake+DuckDB introspect/execute on ADBC; `Query.using()`/CLI on
  Engines; delete `*_connect_kwargs`; finalize public surface
  (`create_engine`/`register`/`get_engine`, no `pool_from_config`/`get_pool`)
- [x] 44-04: Databricks ADBC-introspection spike (gated, autonomous: false) — Path B
  (`NotImplementedError` fallback + standalone spike; live introspection deferred at
  the time because the Foundry driver was believed absent)
- [x] 44-05: Integration fixtures → Engine API + cassette-stays-green replay gate
  (7/7 Snowflake cassettes replay GREEN; cassettes byte-unchanged, proving the refactor
  never touched SQL-builder output)
- [x] 44-06: Docs migration — every connection example → `create_engine` /
  `register(engine)` across all 12 documentation pages (clean break); `connection-pools.rst`
  rebuilt as the canonical two-pattern guide

**Details:**
`create_engine(config | name)` constructs an `Engine` that owns one adbc-poolhouse pool
plus its dialect-from-config; the `Engine` base gained `connect()` and a concrete ADBC
`execute()`. Snowflake and DuckDB `introspect()`/`execute()` run over the engine's pool
(`SHOW COLUMNS` / two-pass `DESCRIBE` parsers unchanged). The 3-arg
`register(name, pool, dialect)` and the `pool_from_config`/`create_pool`/`get_pool`
surface were deleted. Documentation was migrated wholesale to the new API.

### Phase 45: Databricks ADBC Query Support

**Goal**: Make Databricks query execution work end-to-end over real ADBC and record the
Databricks integration cassettes (only Snowflake cassettes existed before; 7 Databricks
`test_queries.py` tests were known-failing).
**Depends on**: Phase 44 (Engine owns the ADBC pool + dialect)
**Plans**: 3 plans in 2 waves

Plans:

- [x] 45-01: Databricks `.where()` literal-inlining — `supports_parameterized_queries`
  flag + a single audited `render_literal()` escaper + a build-time post-pass; Snowflake
  and DuckDB stay on `?` + bound params (DBX-01 / 01b / 01c)
- [x] 45-02: Cross-repo adbc-poolhouse DSN fix — `to_adbc_kwargs()` appends URL-encoded
  `?catalog=&schema=` to the decomposed Databricks DSN (released as poolhouse 1.3.1),
  consumed here via a pin bump (DBX-02)
- [x] 45-03: Live-record + commit the 7 Databricks cassettes; `pytest tests/integration`
  replays 14/14 green (7 Databricks + 7 Snowflake) with no live warehouse (DBX-03)

**Details:**
The arrow-adbc Databricks driver rejects parameterized queries (`NOT_IMPLEMENTED`) and
has no default catalog/schema. Phase 45 solved both: a `Dialect.supports_parameterized_queries`
flag (True everywhere except `DatabricksDialect`) routes Databricks through a
`SQLBuilder._render_literal_sql` post-pass that inlines audited Spark-SQL literals and
returns empty params, while Snowflake/DuckDB keep `?` + params; and the poolhouse DSN
fix carries `catalog`/`schema` so unqualified `FROM \`sales_view\`` resolves. Local
requirement IDs only (no `REQUIREMENTS.md`): DBX-01, DBX-01b, DBX-01c, DBX-02, DBX-03.

### Phase 44-04 follow-up: Databricks ADBC introspection (post-Phase-45)

After Phase 45's cassette recording proved the ADBC Databricks driver was in fact live
on the dev machine, the Phase 44-04 `NotImplementedError` fallback was retired.
`DatabricksEngine.introspect()` now parses `DESCRIBE TABLE EXTENDED <view> AS JSON` over
ADBC (byte-identical to native), mapping `is_measure`→metric / else→dimension and
`type.name`→Python type, mirroring `SnowflakeEngine`. ADBC `ProgrammingError`/`OperationalError`
map to `SemolinaViewNotFoundError`/`SemolinaConnectionError`. An introspect cassette was
recorded and replays green in CI; the `NotImplementedError` unit/e2e tests and
`scripts/spike_databricks_adbc_introspect.py` were removed (commit f94418d).

## Milestone Summary

**Decimal Phases:** None.

**Key Decisions:**

- Engine owns the pool (SQLAlchemy-style): `create_engine(config | name)` builds an
  `Engine` owning one ADBC pool + dialect-from-config; `register("name", engine)` and
  `get_engine` replace the `(pool, dialect)` tuple registry
- ADBC-only: native backend connectors and `*_connect_kwargs` deleted — one transport
  stack for introspection and execution
- Clean break, no deprecation (pre-1.0): the v0.5 `pool_from_config`/3-arg `register`
  surface was removed outright and all docs migrated in the same milestone
- Databricks `.where()` via literal-inlining behind a `supports_parameterized_queries`
  capability flag + one audited `render_literal` escaper, rather than gating `.where()`
  as unsupported — keeps the query API uniform across backends
- Cross-repo fix landed upstream in adbc-poolhouse (1.3.1) and consumed via a pin bump,
  not worked around locally
- Cassette-stays-green replay gate: the refactor is proven safe by Snowflake cassettes
  replaying byte-identical, not by re-recording

**Issues Resolved:**

- Engine/pool/dialect split collapsed into one `Engine` object
- Databricks query execution blockers (no bind params, no default catalog/schema)
- Databricks ADBC introspection (`NotImplementedError` fallback retired post-Phase-45)
- First Databricks integration cassettes recorded — `tests/integration` now 14/14 green
  offline

**Issues Deferred:** None specific to v0.6. Backlog (17 pending todos) carried forward
as next-milestone candidates.

**Technical Debt Incurred:**

- No standalone `v0.6-MILESTONE-AUDIT.md` was produced — the milestone was verified
  per-phase (44/45 VERIFICATION.md) and via the green PR #33 CI (basedpyright strict,
  ruff, pytest 3.11/3.14, `[duckdb]` smoke), not a separate cross-phase audit run.
- `render_literal` covers str/int/float/bool/None only — Date/Decimal literals raise
  `NotImplementedError` on Databricks until a real case needs them.
