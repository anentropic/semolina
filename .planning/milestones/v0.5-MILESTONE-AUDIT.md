## Notes for Future Milestones

1. **Lesson #1 (API-name vs requirement-text drift) is CLEAN for v0.5.** Every requirement's named
   API exists under exactly that name in shipped code, re-grep-confirmed this audit:
   `fetch_record_batch` (`cursor.py:164`), `__iter__`/`__next__` (`cursor.py:222`/`:237`),
   `_normalize_database_path` (`cli/codegen.py:29`), the three metadata queries
   (`duckdb.py:202`, `snowflake.py:328`, `databricks.py:330`), and the strict role map
   (`python_renderer.py:22`/`:66`/`:84`). This contrasts with v0.4.0 `ARROW-02`, where the
   requirement text said `to_arrow()` while the shipped API was `fetch_arrow_table()`. v0.5 does
   **not** repeat that drift.

2. **Lesson #2 (traceability consistency) — one finding, reconciled in this phase.** REQUIREMENTS.md
   lists STREAM-01 (`:14`) and STREAM-02 (`:15`) as unchecked `- [ ]` while the Traceability table
   (`:63-64`) marks both `Complete` for Phase 39. The checkboxes are the stale side — Phase 39 is
   `[x]` in ROADMAP and 39-VERIFICATION is `passed`; the Phase 39 close edited the table rows but
   missed the two carryover-preamble checkboxes (the same "table edited, list not" drift the v0.4.0
   audit warned about). This is a **documentation/traceability** finding, not a functional gap, so
   it does not block `status: passed`. **Disposition (SC3):** fix in-phase via Plan 02, which also
   amends ROADMAP SC1 wording (`v0.5-UAT-AUDIT.md` → `v0.5-MILESTONE-AUDIT.md`) and flips AUDIT-01
   to Complete gated on this verdict.

3. **Report naming/placement.** This report is `.planning/v0.5-MILESTONE-AUDIT.md` at the
   `.planning/` root (NOT `v0.5-UAT-AUDIT.md`, NOT pre-placed in `milestones/`). The
   `milestone.complete` handler globs exactly `.planning/v{version}-MILESTONE-AUDIT.md` in root and
   moves it into `milestones/` itself; the `UAT-AUDIT` name SC1 literally specifies would be
   silently left un-archived.
