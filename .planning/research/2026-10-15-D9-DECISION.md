# D9: how `--check` should read committed files

**Date:** 2026-10-15. **Plan:** 55-05, a blocking checkpoint. **Decides:** D9, and through it
GEN-11 and GEN-12. **Builds on:** `2026-09-30-CHECK-ACCURACY.md`, which lists the cases and
the alternatives. This note measures them.

## What was done

1. **Every case became a test.** `tests/unit/codegen/test_check_accuracy_corpus.py` has one
   test per case, asserting the exit code `--check` *should* give. The 20 that fail today
   are marked as expected failures in strict mode: pytest counts them as passing while they
   fail, and fails the run the moment one starts passing, so whoever implements D9 has to
   remove each marker on purpose. Every one was run unmarked and seen to fail on its exit
   code, not on a crash. Nine more tests pass today and stay that way: four are cases that
   already behave (M10, D2's `alias=` half, D3 judged by the fast path, D5), and five are
   controls, real drift that any fix must still report (`Optional[int]` for a decimal
   column, a dropped `None`, an aliased field with the wrong type, a drifted class placed
   last, `Optional[int]` in a DTO). M7 and M8 are not in this file: they are GEN-09, which
   55-04 is fixing.
2. **Each alternative was prototyped** under `.planning/research/d9-prototypes/`, as
   throwaway code patched into the real CLI. `run_corpus.py` runs the corpus once per
   alternative, with the markers ignored, and records which tests pass. Nothing in `src/`
   changed.
3. **C's isolation was measured** by `c_isolation.py`, as root and again as an unprivileged
   user.

The alternatives, in one line each:

- **A**, a smarter text reader: names resolved through the file's own imports, annotated
  assignments, `view=` from a constant, base classes in the same file.
- **A+**, as A, and also following imports into other modules under the working directory,
  by finding and parsing their source.
- **B**, comparing types instead of strings. Both annotations are reduced to a set of fully
  qualified names, so `Optional[int]`, `int | None` and `None | int` compare equal. Only
  names from an allowlist of modules (`builtins`, `typing`, `decimal`, `datetime`, `uuid`,
  `semolina.types`, `pydantic`) are resolved, and nothing is called. On its own B cannot
  know what a bare `Decimal` refers to; with A it can.
- **G**, a static-analysis library (griffe or astroid) reads the file, resolves its names,
  follows its base classes and finds its constants, without importing it. Annotations then
  go through B's comparison.
- **C**, importing the committed file in a child process that is given no credentials.
- **R**, matching rules, which none of the above touch: view names compared the way DuckDB
  compares identifiers, every class for a view checked rather than the last, a renamed
  field matched by the column it reads, a renamed DTO class matched by its provenance
  docstring.
- **E**, for DTOs, an opt-in mode that judges a field by what `.into(..., validate=True)`
  would accept rather than by the exact type.

D (a runtime check API for the user's own test suite) and F (a generation manifest) were
not prototyped: neither changes how the CLI reads a file.

### Beyond the corpus

A+ and G tie on the corpus, so `reexport_check.py` tried three ordinary project layouts the
corpus does not contain:

| Layout | A+ | griffe | astroid |
|--------|----|--------|---------|
| base class re-exported through a package `__init__` (`from app import Commerce`) | missed, with a warning | read | read |
| relative import (`from .base import Commerce`) | read | read | read |
| `view=names.SALES_VIEW` (a constant reached through a module attribute) | missed, with a warning | read | read |

A+ could be taught both, but that is the point of the research note's warning: a reader
that follows imports grows into a partial reimplementation of Python's import system, one
layout at a time. griffe and astroid already are one.

In every miss the prototypes print a warning naming the class and the statement, rather
than dropping the field silently. That is GEN-12's "no field-like statement is skipped
silently", and it is cheap whichever reader is chosen.

## Does C keep credentials away from the user's module?

No. `c_isolation.py` set up a project holding every credential source Semolina reads
(`.semolina.toml`, a `.env` file, `SNOWFLAKE_*` and `DATABRICKS_*` environment variables)
plus a driver credentials file in the home directory. A parent process playing the CLI held
the secrets in its environment and an open socket standing in for the warehouse connection,
and ran the committed file in a child whose environment was an allowlist (`PATH`, `LANG`
and similar, nothing else). The committed file's module-level code then looked for
credentials. Measured twice: as root, and with both processes dropped to `nobody`, the
ordinary case of a CLI and its child running as the same unprivileged user. The results
were the same both times except where noted.

| What the user's module tried | Result |
|------------------------------|--------|
| its own environment variables | **clean**: no secret reached the child |
| the parent's open connection | **clean**: no descriptor was inherited |
| `.semolina.toml`, by relative path or next to its own `__file__` | **read** |
| `.env` next to its own `__file__` | **read** |
| `semolina.config.warehouse_config("snowflake")` | **returned the password** (root run; the `nobody` run had no Semolina install to call) |
| the parent's environment, through `/proc/<parent pid>/environ` | **read**: `SNOWFLAKE_PASSWORD`, `DATABRICKS_TOKEN` |
| the parent's `HOME` from the same file, then `~/.snowflake/connections.toml` | **read** |

A credential-free environment hides only the one thing an attacker least needs. Credentials
live on disk, where a process running as the same user can read them, and on Linux even the
parent's environment can be read back through `/proc`. Real isolation would need an OS
sandbox (a container, Landlock, macOS `sandbox-exec`), which is per-platform and outside
what a pip-installed CLI can promise. The module also keeps network access, so whatever it
reads it can send.

So C should be described honestly: it is "trust this file", like `codegen-dto`'s dotted
query path already is (T-50-02), and not "safe to run on an untrusted file". If an
importing check is wanted, D is the better home for it, because there the user's own test
suite imports the models and the trust decision is plainly theirs.

## Cost of each alternative

Sizes count non-blank, non-comment prototype lines. Production code would add docstrings,
error messages and tests, so treat them as relative, not absolute. Today's model reader is
219 lines.

| Alternative | Prototype size | New dependency | Runs the user's code | Notes |
|-------------|----------------|----------------|----------------------|-------|
| A | about 200 (reader 165, import table and helpers) | none | no | same-file bases and constants only; others warn |
| A+ | A plus about 30 | none | no | misses re-exports and module-attribute constants (above); grows with every layout |
| B | about 85 (the type reducer) | none | no | needed by A, G and C alike: something must compare two annotations |
| G griffe | 106, plus B | `griffelib` 2.3.2: 0.7 MB, no dependencies of its own (the `griffe` meta-package adds a CLI and `colorama`, which `--check` does not need) | no; `allow_inspection=False` forbids falling back to an import | search paths passed as an argument, no global state |
| G astroid | 111, plus B | `astroid` 4.x: 1.1 MB, no dependencies; already in `uv.lock` for the docs build | no user code; it does import stdlib C extensions to describe them | finds other modules through `sys.path`, so the working directory has to be appended to `sys.path` for the duration of a read; 20 times slower than griffe here |
| C | 165 (child and parent), plus B for the generated side | none | yes, all of it | does not isolate credentials (above); needs the file to be importable; `JsonValue` and string annotations need special handling; about 1 s per file |
| R | 95 | none | no | four independent rules; M4's should ask the engine how it resolves names rather than assume DuckDB's |
| E | 73 | none | no; types come from B's allowlist, the tested values are synthetic | adds a flag, `--validate`; only useful with B or G |

## Recommendation

Use griffe (the `griffelib` distribution, in the `[cli]` extra D6 creates) as the model
reader, with B's type reduction for both commands, and add the four matching rules (R) and
the `AliasChoices` reader rule, none of which depend on the reader. Measured, that fixes 19
of the 20 failing cases with no user code run, and the 20th is the fifteen-line rule the A
prototype already has. Every miss is reported as a warning naming what was not read. Leave
D3 to an opt-in `--validate` flag (E), and only if Paul wants deliberate narrowing
supported; otherwise record D3 as an accepted limitation, alongside M10 and D5. Do not
build C: it runs the file, and the isolation that was its reason to exist does not hold. If
an importing check is wanted later, build D, where the user's tests already import their
models. If Paul would rather add no dependency, the fallback is A with B (same-file bases
and constants only, the rest warned about), which with R and E fixes 18 of 20 and leaves
cross-module bases and constants as documented limitations. griffe is preferred over
astroid because it is faster, smaller, built for exactly this job (reading an API without
importing it), and takes its search paths as an argument instead of through `sys.path`.

## Questions only Paul can answer

1. **Is a hand-edited generated file a supported input?** If yes, the matching rules for a
   renamed attribute (M5) and a renamed DTO class (D4), and the `AliasChoices` rule (D2),
   are fixes. If any hand edit should read as drift by design, those three tests become
   documented limitations instead, and R shrinks to M4 and M9.
2. **May the `[cli]` extra take a dependency on `griffelib`** (0.7 MB, no dependencies of
   its own)? If not, A with B is the fallback, with cross-module bases and constants
   reported as not followed.
3. **How should a view name on the command line match `view=`?** The prototype folds names
   the way DuckDB does. Snowflake folds unquoted names to upper case and keeps quoted names
   case-sensitive. Should the check ask each engine to resolve both names, or match on the
   resolved catalog object?
4. **Two classes for one view (M9): check both, or refuse the file as ambiguous?** The
   prototype checks both and reports each.
5. **Should D3's deliberate narrowing be supported through a `--validate` flag (E)**, or
   recorded as a limitation, with the advice to keep a narrowed DTO out of `--check`?
6. **Drop C?** The measurement says it does not isolate credentials. Keeping it would mean
   documenting it as "imports your file", like the dotted query path.
7. **D, a runtime check API for the user's own tests: v0.7 or v0.8?** It is the only place
   an importing check is honest about trust.
8. **Accept M10 (the probe is always unfiltered) and D5 (a generated `Any` accepts any
   annotation) as documented limitations?** GEN-12 asks D9 to accept them explicitly.
