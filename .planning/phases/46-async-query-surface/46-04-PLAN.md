<objective>
Give the async surface its named-engine registry and its query-builder entry point, then export
the whole thing publicly.

D-05 chose separate registries for sync and async engines over one registry holding a union,
for cleaner typing and to stop `.using("reports").aexecute()` from failing at runtime because
the name happened to hold a sync engine. This plan builds that second store, and closes the
teardown hazard RESEARCH Finding 3 identified: `registry.reset()` is autouse-invoked after
every test and is synchronous, so it cannot await `AsyncEngine.dispose()` and must tear async
pools down inline instead — easy to miss right up until the autouse fixture starts leaking
pools between tests.

Purpose: complete ASYNC-02, and make the async surface reachable from `import semolina` rather
than only from a submodule path.
Output: three async registry functions, an async-aware `reset()`, `_Query.aexecute()`, five new
public exports, and unit coverage.
</objective>

## Naming settled here (D-05's discretionary surface)

- `semolina.registry.register_async_engine(name: str, engine: AsyncEngine) -> None`
- `semolina.registry.get_async_engine(name: str | None = None) -> AsyncEngine`
- `semolina.registry.unregister_async_engine(name: str) -> None`
- module-level store `_async_engines: dict[str, AsyncEngine]`, reusing the existing
  `_default_name` constant

RESEARCH Assumption A6 suggested `register_async` / `get_async_engine` / `unregister_async` and
marked the choice explicitly discretionary. This plan diverges on the two verb names, and the
reason is recorded rather than left implicit: an `_async` **verb** suffix reads as "this
function is a coroutine", which is the exact mode confusion D-05 and D-06 were both chosen to
eliminate. `register_async_engine` reads as "register the async engine" and cannot be
misread, and it matches `create_async_engine`'s adjective-before-noun shape. All three are
plain `def`, not coroutines.
</interface_contract>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-supplied engine name → registry lookup | A name string selects which pool a query runs against |
| test teardown → pool lifetime | The autouse reset is the only thing returning test-created pools to the OS |

## STRIDE Threat Register (ASVS L1, blocking threshold: high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-46-10 | Tampering | registry lookup by name | medium | mitigate | Two separate stores (D-05) so an async lookup can never return a sync engine, and a `<behavior>` line plus a test assert that a name present only in the sync store makes `get_async_engine` raise rather than fall back. A union-in-one-dict design would have made a wrong-kind resolution a runtime attribute error deep inside execution. |
| T-46-02 | Denial of Service | `registry.reset()` async teardown | high | mitigate | `reset()` stays synchronous and tears async pools down inline via poolhouse's sync close on the inner pool, because it is autouse-invoked with no running loop. Calling the async pool's own close there would return an un-awaited coroutine and close nothing, leaking a pool per test. Task 1's reset test asserts the pool was actually torn down, not merely that the dict was cleared. |
| T-46-06 | Information Disclosure | `get_async_engine` miss message | low | accept | The message lists registered engine names and a static how-to-fix hint, matching the existing sync message. Engine names are user-chosen labels, not credentials, and no config field or connection string is interpolated. |
| T-46-11 | Denial of Service | eager exports in `__init__.py` | medium | mitigate | Eager exports are the one change that could pull poolhouse's async subpackage — and therefore anyio — into a plain non-async install, breaking `import semolina` for every base-install user. Task 2 re-asserts the subprocess no-anyio check and re-runs Plan 01's packaging test, so the regression cannot land silently. |
</threat_model>
