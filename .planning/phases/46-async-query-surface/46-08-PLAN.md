Establish the framework fact first, and establish it by reading rather than by assuming.
Check the installed Starlette's `request_response`: as installed here it awaits the
handler directly and does not race it against a disconnect watcher, so a client going away
does not by itself cancel a running handler — the ASGI server delivers `http.disconnect` on
the receive channel, and a handler that never reads from it never notices. Verify this
against the installed source **and** against current Starlette documentation or source
before writing. If current Starlette behaves differently from the version installed here,
write what is true and name the version you checked. Do not assert the framework's
behaviour on this plan's say-so.

Then give the reader the consequence and the remedy. The consequence is that an abandoned
request keeps computing and keeps costing, because nothing has cancelled anything yet. The
remedy is to turn the disconnect into a cancellation yourself: run the query inside a task
group alongside a short poll of `await request.is_disconnected()` (confirm from the
installed source that it is a non-blocking poll returning `bool`), and cancel the
surrounding scope when it returns true. Keep the snippet compact — a how-to shows the key
concept and the reader supplies their setup.

Then state what Semolina does once that cancellation lands, cross-referencing
`howto-web-api-timeouts` rather than repeating it: the warehouse query aborts, `aexecute()`
