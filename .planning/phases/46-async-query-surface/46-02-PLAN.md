<objective>
Deliver the async query path end to end, then build it out. The leading task is a tracer:
one real path from `create_async_engine` through `AsyncEngine.aexecute` into
`AsyncSemolinaCursor` and out as `Row` objects via `async for`, working against real DuckDB
under both asyncio and Trio, committed and verified before any expansion. The two expansion
tasks then fill in the rest of the cursor surface and prove the loop stays free under
concurrency.

This is where the phase's risk lives. Connection lifetime is the highest-risk area
(CONTEXT.md says so, RESEARCH makes it concrete): poolhouse holds a reader-lifetime lock on
the connection, and both `AsyncCursor.close()` and `AsyncConnection.close()` take the
foreign tier of that guard, so closing either before the reader raises `ConnectionBusyError`
from inside teardown.

Purpose: prove the architecture on the executor's best early-context tokens, so an
architectural dead end surfaces after one commit rather than after six.
Output: `AsyncEngine`, `AsyncSemolinaCursor`, `create_async_engine`, two DuckDB async
fixtures, and unit coverage for ASYNC-01 and ASYNC-03 across both loop backends.
</objective>

## Public surface this plan creates (the discretionary naming, settled here)

CONTEXT.md left four naming and shape choices to the planner. They are settled as follows so
Plans 03-06 can be written against them without re-deriving:

- **`semolina.config.create_async_engine`** — the separate constructor D-01 locks in, returning
  a distinct `AsyncEngine` type that owns exactly one poolhouse async pool, with the sync-versus-
  async mode fixed at construction. This mirrors SQLAlchemy, where the async constructor is
  likewise a distinct function returning a distinct engine type with its own pool class.
- **`semolina.engines.abase.AsyncEngine`** — concrete (not abstract). `introspect()` is the
  only abstract method on `Engine` and async introspection is deferred to ASYNC-F2, so no
  per-backend async subclasses exist (RESEARCH Assumption A4).
  - `__init__(self, *, pool: Any, dialect: Dialect, config: Any = None)`
  - `async def connect(self) -> Any`
  - `async def aexecute(self, query: _Query) -> AsyncSemolinaCursor`
  - `async def dispose(self) -> None`
- **`semolina.acursor.AsyncSemolinaCursor`** — the D-06 discretionary name. Chosen over an
  `a`-prefixed twin because the type is already distinct, so the prefix would carry no
  information the reader does not already have from the constructor they called.
- **`aexecute()` returns an already-open cursor**, so the call site reads
  `async with await engine.aexecute(q) as cur:`. Chosen over returning an async context
  manager because ASYNC-01's own wording is `await engine.aexecute(query)`, and because it
  keeps `aexecute` a straight mirror of sync `execute()` — one shape difference between the
  two surfaces, not two.
- **Fetch methods keep their sync names and are awaited** (user-resolved Q1):
  `await cur.fetchall_rows()`, not `await cur.afetchall_rows()`.
- **`fetch_arrow_table()` gets its async twin now** (user-resolved Q4): a two-line delegation
  that needs no reader, so no close-ordering care, and it gives the streaming tests an
  independent oracle.
- **`ConnectionBusyError` propagates unwrapped** (D-20, resolved by the user as Q5). D-20 asks
  that this new failure mode — it has no sync analogue — carry an actionable message; poolhouse's
  already tells the reader to check out a separate connection per task, so Semolina documents it
  rather than re-wrapping it and degrading the message.

The async registry surface (`register_async_engine` / `get_async_engine` /
`unregister_async_engine`) and `_Query.aexecute()` are Plan 04's; this plan's tests call
`engine.aexecute(query)` directly.

## STRIDE Threat Register (ASVS L1, blocking threshold: high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-46-02 | Denial of Service | `AsyncSemolinaCursor.aclose`, `AsyncEngine.aexecute` error path | high | mitigate | Ordered close (reader, cursor, connection) with each step suppressed narrowly so teardown cannot raise out; `except BaseException:` in `aexecute` releases the slot before re-raising so a failed cursor creation or execute does not leak; Task 2's close test and Task 3's concurrency test both assert the inner pool's `checkedout()` returns to 0. **Residual, accepted and documented:** no `__del__` rescue is possible on the async path, so a cursor closed by neither `async with` nor `aclose()` leaks a slot permanently — the warn-only finalizer and the docstrings state this rather than claiming parity with the sync cursor. |
| T-46-01 | Denial of Service | concurrency bound | medium | transfer | The bound is poolhouse's own per-pool capacity limiter, sized to pool size plus overflow rather than a library-global default. Semolina adds no second bound; Task 3's acceptance criteria assert its library diff is empty. |
| T-46-04 | Tampering | shared connection across tasks | medium | transfer | poolhouse's connection guard rejects a second concurrent user with `ConnectionBusyError` rather than serializing them, which would let two tasks' statements interleave inside one transaction — driver-safe but logically corrupt, and silent. Semolina propagates it unwrapped and documents it (user-resolved Q5); `aexecute` checks out one connection per call, so a user can only reach it by deliberately sharing. |
| T-46-06 | Information Disclosure | the re-labelled async `ImportError` | medium | mitigate | The message is a static literal naming `semolina[async]`; the action forbids interpolating any config field, path, or credential into it. |
| T-46-08 | Tampering | SQL generation on the async path | low | accept | The async path calls the same `build_select_with_params()` the sync path calls, byte-identically (D-04), so Phase 45's literal-escaping and parameterization controls apply verbatim.
