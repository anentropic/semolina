From `src/semolina/cursor.py`:
```python
class SemolinaCursor:
    def fetch_arrow_table(self) -> pyarrow.Table: ...
    def fetch_record_batch(self) -> pyarrow.RecordBatchReader: ...
    def __iter__(self) -> SemolinaCursor: ...   # returns self; single-pass
    def __next__(self) -> Row: ...              # lazy batch pull; OSError->StopIteration
    def fetchone(self) -> tuple[Any, ...] | None: ...
    def fetchall(self) -> list[tuple[Any, ...]]: ...
    def fetchmany(self, size: int) -> list[tuple[Any, ...]]: ...
    def close(self) -> None: ...
```

Phase 39 verified behaviours (sources: 39-RESEARCH.md §Common Pitfalls, 39-01-SUMMARY.md "Rule 1 fix"):
- Shared state: all fetch methods consume from the same underlying ADBC stream — pick one consumer per cursor.
- Drained-reader: re-iterating after fetch_arrow_table() or a full iteration yields zero rows (OSError from ADBC is normalised to StopIteration in __next__).
- Empty batches: zero-row batches mid-stream are skipped automatically by SemolinaCursor.__next__; direct RecordBatchReader consumers must skip themselves.
- Batch sizes: driver-controlled, not user-tunable in v0.5 (Snowflake ADBC ~200 queued / 10 concurrent default; DuckDB and Databricks driver-determined). STREAM-04 deferred.
- Cursor lifetime: reader requires the cursor (and its connection) to stay alive — consume inside the context manager (arrow-adbc #1893).
