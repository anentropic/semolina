# Phase 52.1 Summary: Test Suite Soundness

## How "can fail" was proven

Every fix in this phase that claims a test can now fail was checked the same way: change the
source so the behaviour the test guards is wrong, run only that test, expect red, restore.
Where it was useful to show the *old* test was the problem, the old version from `HEAD` was
run against the same change and observed green.

One trap in the harness is worth recording. A change that keeps the file the same size (the
`"DESC"`/`"ASC"` swap below), restored within the same second, leaves Python's cached
bytecode valid for the broken version: `.pyc` invalidation compares whole-second mtime and
size. The next full run then failed three unrelated-looking tests. The harness now restores
with the original mtime and clears `src/**/__pycache__`. Only that one change was
size-preserving, and it was the last one run, so no earlier result was affected.

### The jaffle-shop warehouse tests could never have passed

`semolina-jaffle-shop/tests/test_warehouse_queries.py` called `len(result)` on the return
of `.execute()`, which is a cursor with no `__len__`. Run against the DuckDB jaffle fixture
(a throwaway module overriding `snowflake_connection`), **all 15 old tests fail with
`TypeError: object of type 'SemolinaCursor' has no len()`**. They skip without Snowflake
credentials, so no run ever reached that line.

Rewritten to fetch rows through the cursor and assert non-empty results with bounds. Where an
ordering was asserted over a metrics-only query (a single row, so any order passes), a
dimension was added so there are rows to order. `test_null_handling_in_results`, whose own
comment said it "passes regardless", was deleted. Against DuckDB the new file passes 14/14,
and flipping the builder's sort direction fails both ordering tests.

They still cannot pass on Snowflake: rows are read by field name, and Snowflake answers
`AGG("ORDER_TOTAL")` until ALIAS-01. 53-04 now runs this file live in its credentialed
session.

### A real bug the weak assertion was hiding

Replacing the workflow test's `len(rows) >= 1` with exact values exposed a cross-backend
correctness bug. On DuckDB, **filtering on a dimension that is not selected changes the
result's grain**: revenue by region filtered to two countries comes back as one row per
(region, country), with an extra `country` column, because the builder adds the filtered
dimension to `semantic_view()`'s dimension list so the outer `WHERE` can see it. Snowflake
and Databricks return one row per region.

This is the dimension half of review finding A7, which ALIAS-05 described only for metrics.
ALIAS-05 is widened to cover it, and it is pinned by a strict xfail
(`test_filtering_on_an_unselected_dimension_keeps_the_selected_grain`, `raises=AssertionError`)
that turns red the day it is fixed. The workflow test now filters on a selected dimension so
it keeps checking exact values instead of sheltering behind the xfail.
