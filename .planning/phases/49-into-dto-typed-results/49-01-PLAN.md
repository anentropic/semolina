<objective>
Prove one typed result end to end — install contract, guard, error module, schema
pre-check, cursor surface, live warehouse — on the single path that matters most, then
leave every seam the rest of the phase builds on already exercised.

The tracer is one DuckDB `DECIMAL(38,2)` metric carried from a live in-memory semantic view
through `cursor.description` -> the structural pre-check -> `arrowmodel` -> a list of
Pydantic instances, and asserted by `isinstance` on the value that comes back. The same
slice proves the negative: the same column declared `float` on the DTO raises
`SemolinaSchemaMismatchError` before a single row moves.

Purpose: `47-DECISIONS.md`'s whole Decimal policy exists to stop a money column silently
becoming a `float`. Research measured that arrowmodel's fast path leaves a `Decimal` in a
`float`-annotated field with no error, and that `validate=True` does something worse — it
coerces to `1.5` and loses the precision, also with no error. The structural pre-check is
the only mechanism in this phase that catches it, on either path. Proving that on one
column first means a wrong pre-check design costs one commit, not six.

Output: four published extras with a regenerated lock, `src/semolina/exceptions.py` with
two flat errors and the `find_spec` guard helper, `arrow_type_to_runtime_type` sharing the
existing predicate cascade, `src/semolina/dto.py` holding the pre-check, `.into()` on the
synchronous cursor, and a live-DuckDB test that proves the Decimal case both ways.
</objective>

<plan_decisions>
Five questions the research left open are decided HERE, not by the executor. Each carries
its reversibility rating per the phase's reversibility gate.

**PD-01 — `.into()` accepts any `type[BaseModel]`, not only `ArrowModel` subclasses.**
Call `arrowmodel.model_convert(model, data, validate=...)` and
`arrowmodel.ArrowModelConverter(model, validate=...)`, never the `ArrowModel.convert` /
`ArrowModel.iter` classmethods. `model_convert(PlainBaseModel, batch)` was measured working.
This removes an inheritance requirement from users' existing DTOs and leaves Phase 50's
generated class free to subclass whatever it likes. Document `ArrowModel` as unnecessary.
— **Reversibility: costly.** Accepting the wider type is a superset; narrowing later breaks
users who passed a plain `BaseModel`.

**PD-02 — an Arrow `int64` column into a `float`-annotated field IS a mismatch.**
`issubclass(int, float)` is False and the fast path really does leave an `int` in that
field — the same class of silent wrong-typing as Decimal→float. No special case, no numeric
tower. This will surprise readers who expect pydantic's lax coercion, so it gets an explicit
sentence in the DTO-06 docs (Plan 07).
— **Reversibility: reversible.** Loosening later un-breaks call sites; it breaks none.

**PD-03 — the polars floor is `polars>=1.0.0` with no upper cap.** polars 1.0.0 was
installed and measured handling both a `pyarrow.Table` and a PyCapsule stream, and mapping
`decimal128` to a native `Decimal` dtype. ADBC already emits a `FutureWarning` that polars
2.0 changes `from_arrow`'s return to a `Series`; a cap in a published extra is itself a
support burden, so record the future break as a todo instead (Task 2).
— **Reversibility: costly** (D-12: a published extra is an install contract).

**PD-04 — the pre-check reads `cursor.description`, never `fetch_arrow_table().schema`.**
D-06 fixes that the check runs always, on both `.into()` and `iter_into()`, off a schema
already in memory with no probe and no round trip; it leaves the source open, and this is the
choice. `description` carries a `pyarrow.DataType` per column, synchronously, on both cursors,
with no reader created and no await. That is what lets Plan 06's async `iter_into` stay a
plain method. One code path across all four call sites.
— **Reversibility: reversible** (internal detail, no public surface).

**PD-05 — `tests/unit/test_type_fidelity_table.py` needs no edit when the artifact's
polars and pydantic cells move.** Resolved by the planner reading the file rather than left
for the executor: `_parse_comparison_table` bounds itself to the `## Field type comparison`
section and stops at the next `##` heading, so it never sees the `## Downstream Decimal
behaviour` rows. The only coupling is `test_committed_table_is_not_stale`, which requires
the regenerated artifact to be committed in the same commit. Recorded here; Plan 03 still
reads and re-runs that module.
— **Reversibility: reversible.**

**PD-06 — Phase 48's scope fence becomes a value-path CONTENT fence, not a file fence.**
Found by the planner, not by the executor: `tests/unit/test_scope_fence.py`
(`FENCED_PATH_PATTERN` at :30, `DEFAULT_BASE_REF = "9f3c8b9"` at :36) fails on ANY diff
naming `src/semolina/{cursor,acursor,results}.py` between the Phase 48 start commit and
HEAD. Phase 49 legitimately adds six methods across `cursor.py` and `acursor.py`, so the
fence turns red at Plan 01's first commit and stays red for the whole phase. Re-pointing
`DEFAULT_BASE_REF` at Phase 49's start commit does not help — the phase's own commits still
touch those files.

The file's own docstring anticipates exactly this: *"a later phase that needs to touch these
modules should have to say so out loud — by re-pointing this constant in the same commit
that records the decision"*. Saying it out loud here: Phase 49 adds methods to the value-path
modules and adds **no value conversion**, so the fence is narrowed to what 47-DECISIONS.md
Decision 1 actually prohibits — a numeric or decimal conversion introduced into the
row-construction code — rather than to the filenames that happen to contain it. `results.py`
stays fenced by path, because Phase 49 has no reason to touch it at all.
— **Reversibility: costly.** A weaker fence is a weaker guarantee for every future phase, and
Decision 1's prohibition was approved at a blocking human checkpoint. Narrowing it is
recorded here and must be restated in the plan SUMMARY so it is visible at phase verification.
