Four facts must appear as prose, not as asides, because each one is otherwise found the hard
way:

  1. **The alias.** A Snowflake result column is named after the expression — the canonical
     spelling read from a committed cassette is `AGG("REVENUE")`, quotes and all. Show the DTO
     field carrying `Field(validation_alias='AGG("REVENUE")')` and say why. Column matching is
     exact string equality on the Arrow field name, resolved as validation alias, then alias,
     then field name. Without this the page works on DuckDB and fails on the reader's actual
     warehouse.
  2. **What `validate=` buys and what it does not.** The default fast path does no per-value
     validation. `validate=True` runs pydantic's full pipeline per row at roughly two to five
     times the cost and raises a `ValidationError` naming the field for a non-coercible value.
     It is NOT the safe mode for money: a `decimal128` column landing in a `float`-annotated
     field is coerced with no error and the precision is gone. The schema pre-check, which
     runs on both settings before any row moves, is what protects that. Say this plainly; a
     reader who infers the opposite has been actively misled.
  3. **`ArrowModel` is optional.** Any `pydantic.BaseModel` subclass works. Mention
     `arrowmodel.ArrowModel` as available, not as required.
  4. **The two `JsonValue` spellings.** A VARIANT column's DTO field is annotated
     `pydantic.JsonValue`. `semolina.JsonValue` is for generated `SemanticView` models, which
     are read as text and never imported by pydantic; used as a DTO annotation it raises
     `RecursionError` during class creation. One sentence and one clear "not this".

satisfy a `float`-annotated field, because there is no numeric tower and the fast path really
would leave an `int` there. Frame it as the same rule that protects the Decimal case, so it
reads as a policy rather than a quirk.

Close with a "See also" section linking `serialization`, `streaming`, `arrow-output`, the
